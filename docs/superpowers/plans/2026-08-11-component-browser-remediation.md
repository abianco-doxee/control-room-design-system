# Control Room 1.0 — Component Browser Remediation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close ~65 component-browser review items across ten phases and cut a clean 1.0, ending with a docs deploy.

**Architecture:** A pnpm monorepo of `@alebianco/cr-*` packages. Components are authored once as Mitosis `.lite.tsx` and compiled to six frameworks; styles are per-component CSS parts; the Component Browser is a generated static page (`packages/docs/public/components.html`) that mounts the *real compiled React components* as live playground islands. Work proceeds on the branch `chore/1.0-browser-remediation`; merging to `main` is what deploys.

**Tech Stack:** Mitosis (`@builder.io/mitosis`), React/Vue/Svelte/Angular/Solid/Qwik outputs, esbuild, Astro + Starlight, Playwright, `node:test`, Biome, changesets.

**Spec:** `docs/superpowers/specs/2026-08-11-component-browser-remediation-design.md`

## Global Constraints

- **Package manager is `pnpm`.** Never `npm` or `bun`.
- **No backward compatibility required.** Breaking API changes are preferred over deprecation shims.
- **Never commit to `main`.** All work lands on `chore/1.0-browser-remediation`. A push to `main` triggers `.github/workflows/deploy.yml` and publishes to GitHub Pages.
- **Author components only in `packages/components/components/*.lite.tsx`.** Never edit `packages/components/dist/**` — it is generated by `pnpm run build:components`.
- **Author CSS only in `packages/styles/styles/components.css`** (1671 lines, the single source of truth). `packages/styles/styles/parts/*.css` are **generated** by `pnpm run build:styles` and carry a "do not edit" header. Editing a part file silently loses the change on the next build.
- **Put each CSS rule inside its own component's section** (found in Task 17). `build-styles.mjs` partitions `components.css` by `/* ── Name ── */` section headers and routes each **whole segment** to one part file. A combined block covering several components lands entirely in whichever part its section maps to, so the other components never receive it — the CSS looks right in the source and is silently missing from their parts. Verify afterwards by grepping the generated `parts/*.css`.
- **Never trust a CSS class name from this plan without checking the markup.** Task 17's brief guessed eight selectors and five were wrong (`.cr-checkbox__box` is really `.cr-check input`, `.cr-pin-input__slot` is `.cr-pin__cell`, `.cr-tags-input` is `.cr-tags`, `.cr-number-field` is `.cr-numberfield`, `.cr-input-group` needed `__addon`). A wrong selector is silently dead — no test catches it. Confirm against the `.lite.tsx`, and confirm the element you target is the one carrying the visible border.
- **`.lite.tsx` files import only from `../lib/`** — never `@alebianco/cr-utils`, which would not resolve across all six Mitosis targets. Shared logic is duplicated into `packages/components/lib/` and pinned with a drift test (the "ported utility" pattern).
- **Mitosis `onUpdate` requires an explicit dependency array:** `onUpdate(() => { … }, [props.foo]);` — see `CrPalette.lite.tsx:89` and `CrModal.lite.tsx:29`.
- **Every component carries the styling contract**: `unstyled?: boolean`, `pt?: any`, `dt?: any`, with `ptClass`/`ptAttrs`/`ptStyle` from `../lib/pt.ts` and a `data-part` on each part. Match the surrounding file exactly.
- **`ISLAND_IDS` in `packages/docs/build/build-showcase.mjs` must match the `DEMOS` keys in `packages/docs/build/showcase-islands.jsx`.** `packages/docs/tests/showcase-islands.spec.mjs` fails the build otherwise.
- **Adding/removing a component ripples to:** `catalog/registry.json` → `catalog/catalog.json`, `ISLAND_IDS` + `DEMOS`, the per-component CSS part in `packages/styles/styles/parts/`, framework barrels (`build:components`, `build:pkg`), `references/*.md`, and the regenerated `llms.txt`/`llms-full.txt`.
- **The catalog has FOUR generated copies, not one** (found the hard way in Task 12, via `verify:skill` failing): `catalog/catalog.json`, `packages/docs/public/catalog.json`, `packages/mcp/data/catalog.json`, and `packages/skill/skills/control-room-design-system/catalog/catalog.json`. The skill bundle also vendors the **whole styles package**, so `packages/skill/skills/control-room-design-system/packages/styles/styles/components.css` needs the same edit as the real one. Always edit `catalog/registry.json` (the source), then run the builds and `pnpm run verify` — the `verify:*` suite is what catches a missed copy.
- **Removing a prop is not finished when the prop is gone.** Clear it from `catalog/registry.json` too, or the Component Browser keeps advertising it: `build-showcase.mjs` renders `entry.variants` verbatim. Better still, replace the entry with the new prop's values rather than just deleting it.
- **Write one changeset per phase** in `.changeset/`, marking breaking changes, so the eventual Version Packages PR carries an accurate migration note.
- **Run `pnpm run lint` before every commit.** Biome is the formatter and linter.

### Task 3: Deterministic prop-table ordering

**Files:**
- Modify: `packages/docs/build/build-showcase.mjs:157-193` (`readProps`, `propsHtml`)

**Interfaces:**
- Consumes: nothing from Tasks 1-2.
- Produces: `readProps(comp)` returning rows in a stable, documented order. W9's regeneration relies on this being deterministic.

`readProps` currently returns props in **source declaration order**, which differs per file, so the review's "props are not always sorted the same way" is accurate. Sorting purely alphabetically would be worse — it would scatter `unstyled`/`pt`/`dt` through the middle of the table. Sort by *category*, then alphabetically within it.

- [ ] **Step 1: Add a stable sort to `readProps`**

At the end of `readProps`, before `return rows.length ? rows : null;`, insert:

```js
  // Deterministic order: required first (callers must supply them), then optional
  // props alphabetically, then the styling-contract trio last — it is boilerplate
  // on every component and repeating it mid-table buries the real API.
  const CONTRACT = { unstyled: 1, pt: 2, dt: 3 };
  rows.sort((a, b) => {
    const ca = CONTRACT[a.prop] || 0;
    const cb = CONTRACT[b.prop] || 0;
    if (ca !== cb) return ca - cb;          // contract trio sinks to the bottom
    if (ca) return ca - cb;                 // and keeps unstyled · pt · dt order
    if (a.req !== b.req) return a.req ? -1 : 1;  // required before optional
    return a.prop.localeCompare(b.prop);
  });
```

- [ ] **Step 2: Rebuild and verify the ordering is applied**

Run:
```bash
pnpm run build:showcase
grep -A6 'props · <code>&lt;CrCalendar' packages/docs/public/components.html | grep -o 'prow__n">[a-zA-Z]*' | head -12
```
Expected: required props first, then optional alphabetically, with `unstyled`, `pt`, `dt` last.

- [ ] **Step 3: Confirm it is stable across two builds**

Run:
```bash
pnpm run build:showcase && shasum packages/docs/public/components.html
pnpm run build:showcase && shasum packages/docs/public/components.html
```
Expected: identical hashes. A non-deterministic generator would make every later phase's diff unreadable.

- [ ] **Step 4: Commit**

```bash

git add packages/docs/build/build-showcase.mjs packages/docs/public/components.html
```

- [ ] **Step 1: Add a reset action to the Playground harness**

Replace the `Playground` function body's return with one that carries a reset button in the controls panel:

```jsx
function Playground({ tag, defs, render, extra }) {
  const initial = () => ({
    ...Object.fromEntries(defs.map((d) => [d.prop, d.default])),
    ...(extra || {}),
  });
  const [state, setState] = useState(initial);
  const set = (k, v) => setState((s) => ({ ...s, [k]: v }));
  const dirty = defs.some((d) => state[d.prop] !== d.default);
  return h(
    "div",
    { className: "pg" },
    h("div", { className: "pg__live" }, render(state, set)),
    h(
      "div",
      { className: "pg__panel" },
      h(
        "div",
        { className: "pg__controls" },
        defs.map((d) => h(Field, { key: d.prop, def: d, value: state[d.prop], set })),
        h(
          "button",
          {
            type: "button",
            className: "pg__reset",
            disabled: !dirty,
            onClick: () => setState(initial()),
          },
          "reset"
        )
      ),
      h("pre", { className: "pg__code" }, snippet(tag, defs, state))
    )
  );
}
```

## Phase W2 · Dead props / seeded generators *(gate)*

Four components paint imperatively in `onMount` and never repaint. Until this lands, no seeded component can be visually evaluated, and any W5-W8 judgement about them is unreliable.

The fix is identical in all four: extract the paint into a callable, invoke it from both `onMount` and `onUpdate`, with an explicit dependency array listing every prop the paint reads.

**Files:**

**Interfaces:**

Open `packages/docs/public/components.html`, find the **Ascii** card, and change `variant` or `seed`. Expected: the canvas does **not** change. That is the defect.

- [ ] **Step 2: Import `onUpdate`**

Change line 1 to:

```tsx
import { onMount, onUpdate, useRef } from "@builder.io/mitosis";
```

- [ ] **Step 3: Move the paint into a `useStore` action and call it from both hooks**

Mitosis hoists `useStore` methods, so the paint body can be shared. Restructure the component as:

```tsx
export default function CrAscii(props: CrAsciiProps) {
  const canvasRef = useRef(null);

  const state = useStore({
    paint() {
      /* …the entire existing onMount body, unchanged… */
    },
  });

  onMount(() => { state.paint(); });
  onUpdate(() => { state.paint(); }, [props.seed, props.variant, props.width, props.height]);

  return <canvas ref={canvasRef} role="presentation" aria-hidden="true" />;
}
```

Move the existing `onMount` body verbatim into `paint()` — do not rewrite the noise maths. Add `useStore` to the import from step 2.

The dependency array must list **every prop the paint reads**: `seed`, `variant`, `width`, `height`. Omitting one reintroduces the bug for that prop only, which is harder to spot than the original.

```ts
export interface RectLike { x?: number; left?: number; y?: number; top?: number; width: number; height: number; }
export interface Viewport { width: number; height: number; }
export interface PositionOptions {
  /** preferred placement, e.g. "bottom-start" (default). `${side}-${align}`. */

  /** gap between anchor and floating element, px (default 6). */
  offset?: number;
  /** min distance from the viewport edge, px (default 8). */

```

Then add a DOM helper:

```ts
/** Apply computePosition to real elements (position: fixed). Returns the final placement. */
export function placeEl(anchorEl: any, floatingEl: any, opts?: PositionOptions): string {
  if (typeof window === "undefined" || !anchorEl || !floatingEl) return "";
  const a = anchorEl.getBoundingClientRect();
  const f = floatingEl.getBoundingClientRect();
  const p = computePosition(a, f, { width: window.innerWidth, height: window.innerHeight }, opts);
  floatingEl.style.position = "fixed";
  floatingEl.style.margin = "0";
  floatingEl.style.left = p.x + "px";
  floatingEl.style.top = p.y + "px";
  floatingEl.setAttribute("data-placement", p.placement);
  return p.placement;
}
```

### Task 41: The deploy gate — STOP and ask

**Files:** none.

**Interfaces:**
- Consumes: Task 40's verified tree.
- Produces: a deployed docs site, **only after explicit user confirmation**.

**Deploying means merging `chore/1.0-browser-remediation` to `main`.** There is no
deploy command: `.github/workflows/deploy.yml` triggers on push to `main` and
publishes to GitHub Pages. `release.yml` also fires but is dormant (gated on the
`RELEASE_ENABLED` repo variable) and would only open a Version Packages PR, so
merging deploys docs **without** publishing to npm.

- [ ] **Step 1: Summarise the branch for the user**

Report: the phases completed, the breaking changes (from the changesets), the
test results from Task 40, and any item from the original review that was **not**
addressed, with the reason.

- [ ] **Step 2: STOP and ask for explicit confirmation**

Do **not** merge or push to `main` autonomously. Ask the user to confirm the
deploy, making clear it publishes the docs site publicly.

- [ ] **Step 3: On confirmation, merge**

```bash
git checkout main
git merge --no-ff chore/1.0-browser-remediation
git push origin main
```

- [ ] **Step 4: Verify the deployment**

Run:
```bash
gh run list --workflow=deploy.yml --limit 3
```
Watch the run to completion and confirm the published site reflects the changes.
If the run fails, report the failure rather than retrying blindly.
